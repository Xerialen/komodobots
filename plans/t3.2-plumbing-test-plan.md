## Principle (from docs/28) — this is a PLUMBING test, it trains NOTHING

`docs/28:76-86` frames Phase-1's live test as **"visual integrity / 'plumbing'"** — *"prove an ML
model can drive the Frogbot movement without crashing … Not testing whether the bot is good yet."*
So T3.2 proves three connections work end-to-end and **deliberately stops there**:

1. an RL loop **reads state** and **sends movement commands** (the engine↔model pipe), with a
   throwaway **naive reward** (the ticket's "+1 for moving forward") — purely to prove the signal flows;
2. an **MSE/RMSE scorer** grades a recorded bot trajectory against the Route-Canon human seed line;
3. the two ends connect on the **real engine** seam (#422 handoff), recorded + scored once.

No reward shaping (that is T5.1), no hyperparameter tuning (T5.3), no rigorous trajectory alignment
(T5.2/#428), no real training, no 4v4. Everything that could be Phase-2 stays Phase-2.

## The central design call — sim seam vs live seam, and the 6-feat ↔ v5 obs gap

T3.2 says "integrated with the engine" + "the RL loop reads state, sends movement commands." There
are **two engine seams in the repo today, both already working**, and they use **different obs**:

- **LIVE seam (the #422 handoff):** `move_world_view.mwv_state_features()` writes a **6-feature**
  vector `[hspeed/320, vz/320, lvm_sin, lvm_cos, moving, pitch/90]`
  (`experiments/ktx_moveprobe/live/move_world_view.h`, `MWV_FEATURE_DIM=6`) into the `move_shm`
  seqlock; a Python `move_fn` reads it and writes back `(fwd,side,jump)`
  (`scripts/move_policy_sidecar.py:228 read_view / :246 write_move / :457 serve_loop`). The engine's
  `mhw_handoff_engaged()` (`move_highway.h`) already latches the Motor Cortex onto a **base-highway
  polyline** baked from Route Canon (`route_canon_dm3.h`, 4 base highways). Proven live by
  `scripts/prewar_movecheck.py` (mode 30, freshness-gated). **This is the old MoveMLP serving path.**
- **SIM seam (where RL will train):** `ml/rl_onspeed.py:199 class PmoveEnv` steps
  `scripts/pmove_sim.py` (pure-stdlib QW physics) with the **v5 goal-conditioned** obs — a 336-dim
  **self-history tensor** (21 SELF × 16 history) **plus** a 13-dim entity × `n_max` pool **and** 5
  action channels (`data/catalog/feature_registry.json` v5; the three are separate policy inputs,
  not summed). Full PPO already implemented: `RLPolicy` (:116), `collect_rollout` (:516),
  `compute_gae` (:596), `ppo_update` (:611), reward in `PmoveEnv.step` (:300).

**The gap:** the live seam is **6-feat**; the RL policy is **v5/336-dim**. Wiring a v5 RL policy onto
the live engine needs the world-view bridge (`mwv_state_features`) extended from 6→v5 — a separate,
larger job (the known train/serve gap, memory `live-bot-test-rig.md`). **A plumbing test must NOT do
that** — it proves the pipes carry *a* policy and *a* trajectory scores, not that the policy is good.

**Resolution (recommended):** prove **both seams minimally, reusing what exists, training nothing**,
with a single shared stdlib MSE scorer as the CI-gated keystone:

| | seam | policy | where | CI |
|---|---|---|---|---|
| **D1** MSE scorer | — | — | new stdlib tool | **gated** (stdlib) |
| **D2** reward + RL-loop smoke | SIM (`PmoveEnv`) | reuse `RLPolicy`, naive reward, ~few iters | `ml/`, torch | ml-tests (non-gating) + on-box |
| **D3** live end-to-end run | LIVE (#422 handoff) | reuse existing **6-feat MoveMLP** sidecar | on-box, owner-gated | not CI |

D2 proves "RL loop reads state / sends commands / reward flows" in the sim. D3 proves the **real**
engine seam carries a policy down a Route-Canon highway, records it (#424), and scores it (D1). D1
is the number the owner watches. **No real training** — deferred to Phase-2, explicitly.

**The one unresolved tension (the central owner decision — Decision #1 below).** NotebookLM's
docs/28-grounded review flagged that Phase-1's standing mandate is **zero training-serving skew**,
and driving D3 with the **6-feat** MoveMLP leaves the **v5 live encoder unproven live** — arguably
the most safety-critical plumbing for Phase-2 serving. The auditor's countervailing read: for a
*plumbing* test, deferring the v5→live bridge is correct (docs/28 M3: "prove an ML model can drive…
not whether it's good"), and the 6-feat encoder we use is itself parity-proven (`test_live_c_parity.py`),
so zero-skew is **honored, not violated** — just not *advanced* on the v5 axis. My read: this is a
real **coverage gap, not a true contradiction** — docs/28 mandates zero-skew (honored) but does not
time-bind the v5-encoder build to T3.2 (M3 is explicitly minimal). It is a scope/sequencing call the
owner owns; the three options are laid out in Decision #1.

## D1 — `score_route_mse.py` (the keystone)

Schema of the emitted artifact `komodobots.route_mse.v1`:

```
{ "schema":"komodobots.route_mse.v1", "map":"dm3",
  "highway_id":"ra_tunnel_mega_rl",            // EXPLICIT — caller names the highway the bot drove
  "ground_truth":{"source":"route_canon.dm3.json","seed":{...},"n_pts":N},
  "attempt":{"source":"<mvd or sim>","n_pts":M},
  "grid":{"kind":"arclen","n":64},             // common resample grid (arc-fraction by default)
  "mse_xyz":<float>, "rmse_xyz":<float>, "rmse_xy":<float>, "rmse_z":<float>,
  "per_axis_mse":{"x":..,"y":..,"z":..},
  "_scoring":"Minimal honest plumbing MSE: resample BOTH trajectories to a common arc-fraction grid, "
             "mean of squared per-point L2 over (x,y,z) in QUAKE UNITS (qu). Arc-fraction makes this "
             "PATH-SHAPE only — BLIND to speed/timing (two runs of the same path at different speeds "
             "score ~0); use --grid time for timing-sensitive scoring. NOT the rigorous variable-dt "
             "alignment — #428 (T5.2) owns that. Scored vs ONE human SEED line (#420), not the band "
             "(#421, a Phase-1 M2 artifact whose believability-envelope use is a later concern). "
             "A plumbing number, not a quality verdict.",
  "_match":"highway_id is passed in (the live run knows which highway it drove) — NEVER auto-matched "
           "by (from,to) resource pair (#421 _match_key / move_highway.h)." }
```

Algorithm (pure stdlib `math`):
1. Load the named highway and **concatenate its `segments[].trajectory` in order** (a highway can
   have >1 segment — e.g. a teleport chain has `n_segments=2`; the seed line is the joined runs).
2. Take the attempt trajectory `[[t,x,y,z],…]` (from the MVD extract, or a sim rollout in the test).
3. **Unit-consistency guard (P1):** compare the (x,y,z) coordinate SPANS of the two trajectories;
   if they differ by ≈8× (one looks like raw 1/8-qu wire values, the other qu) **fail loudly** —
   both inputs must be in **qu**. This stops a future parse path that emits raw 1/8-qu from silently
   corrupting the keystone number. (Note: `route_canon.dm3.json`'s OWN `_scoring` string mislabels
   the unit as "1/8-qu" — a pre-existing #420 artifact defect; out of scope to fix here, flagged
   separately. The data IS qu — verified: interpreting the trajectory as qu reproduces the
   segment's own `signature` path_qu/hs_max.)
4. **Resample both** to a common grid. Default = **arc-fraction** over the **3D** cumulative
   path-length (m=64) — extend `route_canon_band.py:_resample_xy` (which is 2D) to xyz — so unequal
   durations/tick-rates don't bias the error; offer `--grid time` as an alternative. Arc-fraction is
   **path-shape only / speed-blind** (see `_scoring`); the rigorous variable-dt alignment is #428's.
5. MSE = mean over the 64 samples of squared L2 in (x,y,z); also report RMSE and per-axis.
6. Write the artifact + print a one-line summary (`highway_id rmse_xyz=… n=…`). CLI:
   `score_route_mse.py --canon route_canon.dm3.json --highway <id> --attempt <traj.json|mvd> [--grid arclen|time] -o out.json`.

Gated test (`tests/test_score_route_mse.py`, stdlib, synthetic — **no MVD, no torch**):
- identical trajectories ⇒ MSE≈0; a constant +D offset ⇒ rmse≈D; resample boundary inclusivity;
  arc-fraction vs time grid both run; a known triangle vs its midpoint-shifted copy ⇒ expected rmse;
  empty/one-point attempt ⇒ clear error not a crash; **unit-guard fires** on an ≈8× span mismatch;
  **multi-segment** highway concatenates its segment trajectories in order.

## D2 — baseline reward + RL-loop smoke (reuse `ml/rl_onspeed.py`)

- `--baseline-reward`: replace the round-6 reward in `PmoveEnv.step` with the ticket's naive
  **`+1·(forward progress this tick)`** (a few lines, gated behind the flag; the real reward path is
  untouched). Proves the reward signal flows and is finite.
- `--smoke`: run ~a handful of PPO iters on a tiny env batch, assert the rollout has no NaN, GAE +
  value loss are finite, and `save_rl_ckpt` writes — i.e. the RL loop *closes* (state→action→reward→
  update) without crashing. This is the "functioning baseline PPO script integrated with the [sim]
  engine."
- **Synthetic CI path (P2a — avoid the heavy-artifact wall):** `train()` (`rl_onspeed.py:701`)
  requires `--init-ckpt`/`--bsp`/`--norm-artifact`/`--anchors`/`--db`, and `PmoveEnv.__init__:199`
  needs `world, stats, segments` — none of which can be committed (BSP/ckpt/MVD forbidden). So the
  smoke test does NOT call `main()`/`train()`. It builds the env DIRECTLY: a degenerate `WorldModel`
  via its `__init__` (:141, not `load()`), one tiny hand-built reset-segment (a few `self`-dicts), a
  small in-memory `RLPolicy(BroadBCPolicy(small dims))`, then calls `PmoveEnv`/`collect_rollout`/
  `ppo_update` directly. This keeps the CI smoke artifact-free and reproducible.
- `ml/tests/test_rl_baseline_smoke.py` (`@skipUnless(_HAVE_TORCH)`): the synthetic ~5-iter smoke
  above + a stdlib-math check that the baseline reward is +ve for forward motion, −/0 otherwise.
  Runs in `ml-tests.yml` (torch present) and on-box; **not** in the gating floor. (The full
  `train()` path with real artifacts is an on-box-only run, not CI.)

Two operational pins in `T3.2_PLUMBING.md` (P2c):
- **Pin the latched highway:** `mhw_handoff_engaged` latches the *nearest* base highway dynamically
  (it sets `*which`); the operator must READ that latched index from the engine/freshness log and
  pass **exactly that** id to `--highway` — otherwise a silent wrong-highway MSE.
- **Expect a LARGE MSE.** The 6-feat MoveMLP has a known standstill attractor and does not sustain
  bhop / track a highway (memory `live-bot-test-rig`), so D3's MSE will be poor. State this up front:
  D3 proves the *pipes connect + a number comes out*, NOT trajectory quality. A large MSE here is a
  PASS for plumbing.

`T3.2_PLUMBING.md` documents the exact commands + that this uses the **6-feat** serving path on
purpose (the v5-live bridge is deferred — Decision #1). This is the only step that touches the live

## Owner decisions to confirm (resolve before coding)

**Decision #1 — the v5 live encoder / "zero training-serving skew" (the reviewers split here).**
The live #422 seam encodes **6 features**; the RL policy expects **v5**. How T3.2 handles that gap:

- **Option A — 6-feat live, v5 bridge left open (not ticketed).** D3 drives the proven 6-feat
  MoveMLP; the v5 live encoder is whenever-later. Cheapest. NBLM's objection bites hardest: the
  critical v5 plumbing stays silently unproven.
- **Option B — build a minimal v5 live encoder + parity test IN T3.2.** Extend
  `mwv_state_features` 6→v5, mirror `tests/test_live_c_parity.py`, and drive D3 with a **random-init
  v5 `RLPolicy`** (no training needed — quality is irrelevant for plumbing). This directly PROVES
  zero train/serve skew on the v5 obs — the Phase-1 mandate NBLM cites. Cost: a substantial C lift
  (the whole world-view bridge + its own parity burden) — it turns a "plumbing test" into a real
  engine feature, arguably its own ticket.
- **Option C — 6-feat live for the handoff/record/score proof + keep the parity discipline + FILE
  the v5-live-encoder bridge as a NAMED follow-up ticket (it is currently un-ticketed in Phase-1).**
  *Recommended.* Keeps T3.2 a true plumbing test (auditor + docs/28 M3), HONORS zero-skew (the
  6-feat encoder it uses is parity-proven, `test_live_c_parity.py` — no skewed encoder is shipped),
  and converts NBLM's "silently untested" into "explicitly scoped out + ticketed as the next
  de-risk." Reviewer split: **auditor = defer is correct for a plumbing test**; **NBLM = deferring
  leaves the critical v5 plumbing untested**. My read (evidence above): a real coverage GAP, not a
  true contradiction — so make the gap explicit + ticketed (C), unless you want the v5 seam proven
  live now (B).

**Decision #2 — D3 in T3.2 now, or deferred?** Run the live on-box plumbing step inside T3.2
(recommended if Decision #1 = B or C — it's the only step that proves the *real* #422 engine seam,
and #424 + `prewar_movecheck` make it cheap), or ship D1+D2 (gated scorer + sim smoke, which already
satisfy the ticket's three literal deliverables) now and fold the live run into T3.3/Phase-2.

**Decision #3 — MSE grid default:** arc-fraction (recommended — duration/tick-rate-robust, but
speed-blind) vs time-grid (timing-sensitive). Both are implemented; this picks the default.
