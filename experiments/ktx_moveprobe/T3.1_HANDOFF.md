# T3.1 — Commander/Motor-Cortex handoff toggle — #422

Adds the in-game logic that lets the Frogbot ("Commander") **yield movement control to the
ML model ("Motor Cortex") on a trained base highway, and take it back off the highway, without
crashing** (docs/28 Phase 1 → M3 PoC). The handoff is a **geometric C-side gate** layered onto the
existing T0.3 mode-30 live brain: it does **not** change the move policy (still the frozen 6-feat
MoveMLP) — M3's live test is **visual-integrity / plumbing**, not whether the bot is good.

## The new cvar (opt-in — existing T0.3 behavior is unchanged)

| cvar | default | meaning |
|------|---------|---------|
| `k_fb_moveprobe_live_highway_gate[_s<N>]` | `0` (off) | `0` → mode 30 overrides always (today's behavior). `1` → mode 30 overrides **only while ENGAGED on a base highway**; off it, the stock Commander move stays. |

Resolved through the existing per-slot plumbing (`k_fb_moveprobe_<param>_s<N>` → global
`k_fb_moveprobe_<param>`), so it needs no new config mechanism. Default off means
`test_live_c_parity`, `run_live.sh`, and the prior T0.3 evidence are untouched unless a run opts in.

## Gate semantics (the latched conjunction)

The decision is made in C, keyed on **route geometry** (`route_class` + the traced trajectory),
**never** on the `(from_resource,to_resource)` pair. Engage is **intent-first**: among the base
highways whose end the Commander's goal (`self->s.v.goalentity`, decoded via the bounds-checked
`g_edicts[]` index) is heading for (within `R_GOAL` — a loose radius absorbing the mid-corridor
half-route offset), the gate latches the one whose traced polyline is **nearest** the bot, and
**engages it iff** that nearest is within `R_ON` (precise 2D x,y membership). Intent-first (not
global-nearest-first) so that on overlapping dm3 corridors the bot latches the highway it actually
intends to run — not whichever line happens to be a quu closer.

Once latched it stays on **that specific highway** (tracked explicitly) with hysteresis, and
**disengages** (Commander resumes) on ANY of: drifted off its line (`> R_OFF`), **arrived** (within
`R_ARRIVE` of its end), or lost intent (no goal / goal moved away from its end). State is **per-slot
and latched** (C zero-init = disengaged).

| radius | default (qu) | role |
|--------|--------------|------|
| `MHW_R_ON` | 48 | engage: within this of a base polyline |
| `MHW_R_OFF` | 96 | disengage: drifted beyond this (hysteresis, `R_ON < R_OFF`) |
| `MHW_R_ARRIVE` | 64 | disengage: within this of the highway end (arrival) |
| `MHW_R_GOAL` | 256 | intent: goal within this of the highway end |

These are PoC defaults in `move_highway.h`; tune them by-eye in the live run **together with** the
header downsample cap (`--max-pts`, default 72) — a coarse polyline on a high-curvature leg can sit
`> R_ON` off the true path and cause spurious DISENGAGE.

**2D membership (z deferred):** the gate uses (x,y) proximity only (robust to jump arcs). The
generator WARNs when two base polylines pass within `2*R_OFF` in (x,y) — on dm3 several base
highways share corridors, so the WARN fires today; z-disambiguation is deferred until it matters
(`# ponytail: 2D membership; add z only if the overlap WARN fires`).

## Live test (the M3 close)

Run a `run_live.sh`-style scratch session on dm3 (scratch port + scratch gamedir; never the live
ports/gamedir) with the gate on:

```
k_fb_moveprobe_mode_s1 30
k_fb_moveprobe_live_highway_gate_s1 1
k_fb_moveprobe_live_log 1
```

Expect, in `screen.log`: `[moveprobe-handoff] slot N ENGAGED` when the bot heads along a base
highway (intent + on-line) and `... DISENGAGED` elsewhere / on arrival (no spurious engage during
combat), the server ticking continuously (**no freeze**), and the stock fallback still firing when
the sidecar is paused.

**Freshness accounting:** a DISENGAGED frame is also logged as **FALLBACK in the `[moveprobe-live]`
plane** (`live=<live_frames>/<total_frames>`, with `live_frames` flat — the Motor Cortex did not
drive that frame). So `evaluate_live_freshness` (`scripts/run_4v4_validation_lab.py`) — which keys on
the highest-`total` cumulative line — counts off-highway frames, and the `< 1.0` fraction it reports
is the **auditable engaged (on-highway) share**, not a value frozen on a stale total at the last
on-highway line. The `[moveprobe-handoff]` line is the human transition marker; the `[moveprobe-live]`
line is the parseable evidence plane. Record the MVD (the #424 recorder) → run
`experiments/route_observatory/pov_fuse_pipeline.py` (#421) on it → contact sheet + L1 pixel /
integrity green by-eye → emit the contact-sheet path into the #424 ledger's `contact_sheet` field.
That is docs/28 M3's visual-integrity test and the milestone-3 close.

**Freshness fraction with the gate on — read it right.** The `-fraction` per-frame counters increment
`total_frames` every live tick but `live_frames` only when the Motor Cortex actually overrides, which the
gate now suppresses off-highway. So `evaluate_live_freshness` (the #424 recorder's gate) reports a fraction
**< 1.0 by design** for a handoff run — it measures the *engaged* (on-highway) share, not a defect. Judge a
handoff run by the ENGAGED/DISENGAGED transitions + no-freeze, **not** by freshness ≈ 1.0.
