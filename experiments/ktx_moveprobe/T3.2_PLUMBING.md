# T3.2 — Baseline reward signal & scoring, the "plumbing" run — #423

Proves the **end-to-end pipe** works: an ML mover drives the live Frogbot down a base Route-Canon
highway, the run is **recorded** (#424), its trajectory is **extracted**, and it is **scored** against
the human seed line with one MSE number (docs/28 Phase 1 → M3 "visual integrity / plumbing"). It
**trains nothing** and does **not** test whether the bot is good. T3.2 ships three deliverables:

| | seam | what it proves | where |
|---|------|----------------|-------|
| **D1** `score_route_mse.py` | — | a recorded trajectory scores vs the #420 seed (`komodobots.route_mse.v1`) | stdlib, CI-gated (`tests/test_score_route_mse.py`) |
| **D2** `rl_onspeed --baseline-reward --smoke` | SIM (`PmoveEnv`) | the RL loop reads state → sends moves → naive reward flows → PPO updates, no NaN | `ml/`, torch (ml-tests, non-gating + on-box) |
| **D3** this runbook | LIVE (#422 handoff) | the **real** engine seam carries a policy down a highway, records + scores | on-box, owner-gated, NOT CI |

This file is **D3**: the on-box live run. It drives the **existing frozen 6-feat MoveMLP** (the T0.3
mode-30 sidecar) through the #422 handoff gate — **on purpose** (see "Why 6-feat" below). The
v5-obs-live encoder is **deferred**; its follow-up ticket draft is at the bottom of this file.

## Step 1 — record a live mode-30 run on a base highway (#424)

Reuse the proven freshness-gated harness unchanged (`scripts/prewar_movecheck.py`). One bot = no
opponents = no shooting (the lone-mover case):

```bash
# detached (aws-dev reaps the tool-call process group on return); poll for freshness.json
setsid python3 scripts/prewar_movecheck.py --port 28599 --run-for 90 --bots 1 \
    > /tmp/t32.out 2>&1 < /dev/null &
```

To exercise the **handoff** specifically (so the bot latches a base highway and the log names which
one), set the T3.1 gate cvars on the slot (per `T3.1_HANDOFF.md` "Live test"):

```
k_fb_moveprobe_mode_s1 30
k_fb_moveprobe_live_highway_gate_s1 1
k_fb_moveprobe_live_log 1
```

The harness writes a **GREEN/RED freshness verdict** (`live=L/T` — proof the learned model drove the
frames, not the stock fallback), a `freshness.json`, and the recorded **`.mvd`** path. With the gate
on, freshness `< 1.0` is **by design** (it measures the engaged/on-highway share — see
`T3.1_HANDOFF.md` "read it right"), not a defect.

## Step 2 — PIN the latched highway id (the silent-wrong-MSE trap, P2c)

`mhw_handoff_engaged` latches the **nearest** base highway dynamically (it sets `*which`). You MUST
read that latched highway from the engine log and pass **exactly that id** to `--highway` — scoring
against a highway the bot did not drive is a silently-wrong number.

- In `screen.log`, find the `[moveprobe-handoff] slot 1 ENGAGED` line; it identifies the latched
  **base** highway. The index is into the **base-highway order** that
  `gen_route_canon_header.py` emits — i.e. the `route_class=='base'` highways of
  `data/catalog/route_canon.dm3.json` **in file order**. Map index → that highway's `id`.
- Sanity-check it against the bot's path (the ENGAGED line's coordinates vs the highway's
  `start_xyz`/`end_xyz` in the canon). If the bot wandered across several base lines, score only a
  window where it was ENGAGED on **one** highway, or pick the dominant ENGAGED highway.

## Step 3 — extract the attempt trajectory (qu), then score (D1)

Extract the recorded bot's per-tick `[t, x, y, z]` from the MVD with the proven full-view recipe, in
**Quake units (qu)** — the scorer's P1 unit-guard **fails loudly** on raw 1/8-qu wire values:

```bash
# per-tick positions/view/velocity for all players, then slice the bot player + the ENGAGED window
qw-analyze -view full -include positions,view,velocity <run>.mvd > /tmp/full.json
# -> a small slice to [[t,x,y,z],...] for the bot, in qu (see scripts/catalog_etl_qwd.py for the
#    canonical position decode; do NOT invent a 4th parse path). Write it to /tmp/attempt.json
python3 experiments/route_observatory/score_route_mse.py \
    --canon data/catalog/route_canon.dm3.json \
    --highway <latched-id-from-step-2> \
    --attempt /tmp/attempt.json \
    --grid arclen \
    -o /tmp/route_mse.json
```

Output: one line `… rmse_xyz=… rmse_xy=… rmse_z=… n=64 grid=arclen` + the `komodobots.route_mse.v1`
artifact. `--grid arclen` (default) scores **path shape** (speed-blind); use `--grid time` for a
timing-sensitive number. Eyeball the recorded path against the rendered route image (memory
`headless-visual-self-validation`) as a second channel.

## Expect a LARGE MSE — and that is a PASS (P2b)

The frozen **6-feat MoveMLP has a known standstill attractor and does not sustain bhop / track a
highway** (memory `live-bot-test-rig.md`). So D3's `rmse_xyz` **will be poor**, and that is **fine**:
D3 proves *the pipes connect and a number comes out*, **not** trajectory quality. A large MSE here is a
**PASS for plumbing**. The GREEN freshness verdict (the learned model drove the frames) + a finite MSE
number from the real seam = the M3 plumbing close.

## What this does NOT prove (scope boundary)

- **Not** that the bot moves *well* — quality is Phase-2 (RL training, T5.x). A large MSE is expected.
- **Not** the rigorous variable-dt trajectory alignment — arc-fraction MSE is path-shape-only and
  speed-blind; #428 (T5.2) owns the rigorous alignment.
- **Not** the **v5** live encoder — D3 drives the **6-feat** seam (below). The v5-obs live path stays
  unproven live until the deferred bridge ticket lands.
- **Not** a believability-band judgment — D1 scores vs the **one** #420 seed line, never the #421 band.

## Why 6-feat on purpose (the deferred v5-live bridge — Branch C)

The live #422 seam encodes **6 features** (`move_world_view.mwv_state_features`, `MWV_FEATURE_DIM=6`);
the v5 RL policy expects the **336-dim v5 goal-conditioned obs**. Wiring a v5 policy onto the live
engine needs the world-view bridge extended 6→v5 — a **separate, larger job** (the known train/serve
gap). A *plumbing* test must not build it (docs/28 M3 is explicitly minimal). T3.2 chose **Branch C**:
drive D3 with the **parity-proven** 6-feat encoder (`test_live_c_parity.py`) — which **honors** the
docs/28 "zero training-serving skew" mandate (no skewed encoder is shipped) — and **explicitly ticket**
the v5-live bridge as the next de-risk (draft below). Decision recorded in `docs/08_DECISION_LOG.md`.

**Title:** [Phase-1] v5-live world-view encoder bridge (6-feat → v5) + C/Python parity test

**Why now.** T3.2 (#423) proved the live #422 handoff seam carries the frozen **6-feat** MoveMLP and a
recorded trajectory scores (D1). But the actual movement brain docs/28 P1–P3 builds is the **v5**
policy, which consumes the 336-dim goal-conditioned obs (`feature_registry.json` v5). The live engine
does **not** produce that obs — `move_world_view.mwv_state_features` emits only 6 features. So the
**most safety-critical Phase-2 plumbing — a v5 policy driving the live engine with zero train/serve
skew — is currently unproven live.** This ticket closes that gap (NotebookLM's NB-2 objection, surfaced
as T3.2 Decision #1).

**Scope (what to build).**
1. Extend the C world-view encoder `mwv_state_features` (`experiments/ktx_moveprobe/live/move_world_view.{c,h}`)
   from 6 features to the **v5 self/entity/goal channels** the registry defines (raise `MWV_FEATURE_DIM`;
   extend the `move_shm` seqlock layout). Keep it an **opt-in cvar**; the existing 6-feat path stays
   default and untouched.
2. Mirror `tests/test_live_c_parity.py`: assert the C v5 encoder **byte-matches** the Python
   `features/agent_observation.encode_observation` (+ `assemble_self_history`) for a fixture of live
   states — the same parity discipline the 6-feat seam already passes.
3. Drive a live mode-30 run with a **random-init v5 `RLPolicy`** (no training — quality is irrelevant
   for plumbing) through the #422 handoff, record (#424), and confirm GREEN freshness (the v5 policy
   drove the frames) + a finite D1 MSE. This proves the v5 obs flows end-to-end with zero skew.

**Acceptance.** C↔Python v5-obs parity test green; the obs layout matches `feature_registry.json` v5;
a random-init v5 policy drives the live bot without crashing (freshness GREEN) and scores via
`score_route_mse.py`. **No** new `feature_registry` channels (read-only consumer); **no** change to the
move-policy training; the v5-live encoder is behind a default-off cvar.
