**Author:** Claude (Coder), on behalf of Xerial.

## Question

What is the cheapest way to hand a per-tick **action** (move + aim + fire + weapon)
to a bot slot every server tick, and does it clear the Phase-0 budget?

> **Exit (from the ticket):** a written report that NAMES the chosen pipe and shows
> **p99 < ~0.5 ms/tick** for **up to 4 slots at ~77 Hz** (~13 ms/tick wall budget).

## Chosen pipe: **POSIX shared memory (`shm`)**

A small `/dev/shm`-backed region, one fixed record per bot slot, written in place by
the brain sidecar with a per-slot **seqlock** and read by the server frame each tick.
On a native KTX trap this is `shm_open()` + `mmap()`; the benchmark exercises the
identical mechanism from Python via `mmap` over `/dev/shm/<name>`.

It wins on every axis that matters here: lowest p99, lowest jitter (tightest max),
and it scales almost flat with slot count. All three candidates clear the budget, so
the choice comes down to headroom and tail behavior — and `shm` has by far the most of
both.

## Measured p99 (host-local microbenchmark)

Pattern: **single-threaded consumer** (models the KTX bot frame loop) fetching the
freshest action for **all slots once per tick**, paced at the tick rate, while a
separate **producer process** (models the python brain sidecar) writes the freshest
action per slot asynchronously. Action record = the exact `trap_SetBotCMD` payload
(3 move floats + 3 aim/`desired_angle` floats + buttons byte (fire/jump) + impulse
byte (weapon) + cmd_msec), packed identically (32 bytes) for all three transports.

`per-tick` = time to service **all** slots in one frame (this is what competes with the
~13 ms tick budget). `/slot` = per-tick ÷ slots.

### 4 slots @ 77 Hz, 8 s/run, first 77 ticks discarded as warm-up (~539 ticks measured)

| candidate     | p50 (ms) | p95 (ms) | p99 (ms) | p99.9 (ms) | max (ms) | /slot p99 (ms) | verdict |
|---------------|---------:|---------:|---------:|-----------:|---------:|---------------:|:-------:|
| action-file   |   0.0627 |   0.0855 |   0.1058 |     0.1590 |   0.1942 |         0.0264 | PASS    |
| **shm**       |   0.0068 |   0.0095 | **0.0124** |   0.0361 |   0.0581 |         0.0031 | **PASS** |
| socket        |   0.0193 |   0.0289 |   0.0712 |     0.1428 |   0.1455 |         0.0178 | PASS    |

Budget is **0.5 ms/tick**. `shm` per-tick p99 ≈ **0.012 ms** — roughly **40× under budget**.

### Stability across 3 repeat runs (per-tick p99, 4 slots @ 77 Hz)

| candidate   | run 1 | run 2 | run 3 |
|-------------|------:|------:|------:|
| action-file | 0.106 | 0.109 | 0.124 |
| **shm**     | **0.012** | **0.017** | **0.029** |

Ordering `shm < socket < action-file` holds on every run; `shm` is always the lowest

## The three candidates, and why `shm` wins

1. **(a) action-file re-read** — producer atomically rewrites a per-slot file
   (`write tmp` + `os.replace`), consumer re-opens + reads it each tick. Simplest to
   reason about and crash-safe, but every tick pays open/read/close syscalls **per
   slot**, and the producer pays a rename per slot. Slowest and jitteriest of the
   three (open/replace under contention), though still comfortably inside budget. Good
   fallback / debug tap; not the primary.
2. **(b) shm** *(chosen)* — one `mmap` region, fixed record per slot, written in place
   under a lock-free **seqlock** (writer bumps a guard before/after the body; reader
   retries until the two guards match → never a torn read). After the one-time `mmap`,
   a tick read is just a couple of struct unpacks against already-mapped memory: no
   per-tick syscall, no allocation, no copy across a kernel boundary. Lowest latency,
   lowest jitter, flattest scaling.
3. **(c) unix-domain DATAGRAM socket** = the **short action-queue** — producer sends
   one datagram per action; consumer drains the socket each tick and keeps the freshest
   datagram per slot (newest-wins; a full small `SO_RCVBUF` just drops stale frames,
   which is correct for "latest action only"). Naturally bounded and gives clean
   back-pressure semantics, but pays `sendto`/`recv` syscalls every tick. Middle of the
   pack; a fine fallback if the wiring effort of a shared-memory trap is unwanted.

**Decision:** wire **shm** as the live brain pipe. It has the largest tail-latency
margin, no per-tick syscall, and the cleanest scaling to 4+ slots; the **socket** is the
recommended fallback (simplest native wiring, still well inside budget) and the
**action-file** is a useful low-effort debug tap.

## Suggested wiring for T0.3 (so the spike feeds the real patch)

When T0.3 adds the new moveprobe "live mode" to
`experiments/ktx_moveprobe/frogbot-moveprobe-perslot.patch` (consumed by
`artifacts/ktx-live/bot_movement.c`, the `BotApplyMoveProbe` → `trap_SetBotCMD` seam at
~line 6191), the cheapest faithful wiring of the chosen pipe is:

- **One shared region, indexed by slot** (`slot = NUM_FOR_EDICT(self) - 1`, already
  computed in `BotApplyMoveProbe`). Region = `MAX_CLIENTS × sizeof(slot_record)`.
- **Per-slot record** = `{ u32 seq_a; action; u32 seq_b; }` where `action` is exactly the
  `trap_SetBotCMD` argument bundle: `cmd_msec (u16)`, `desired_angle[3] (f32)`,
  `direction[3] (f32)`, `buttons (u8: fire bit0, jump bit1)`, `impulse (u8)`. (This is
  the 32-byte record the benchmark already moves.)
- **Reader (server, in `BotApplyMoveProbe`)**: seqlock read (retry until
  `seq_a == seq_b`), then map fields onto the existing locals (`direction`, `*jumping`,
  `*firing`, `*impulse`, `self->fb.desired_angle`) and fall through to `trap_SetBotCMD`
  exactly as today.
- **Safe fallback (the T0.3 done-when)**: keep a per-slot `last_seq` + a freshness
  deadline; if `seq` has not advanced within N ticks (helper slow/dead), **do not freeze**
  — fall back to the existing stock-frogbot path for that slot and log it. The seqlock
  also guards the slow-helper case: a partial write is simply re-read, never applied torn.
- **Writer (python brain sidecar, T0.6)**: `mmap` the same `/dev/shm` region and write
  each slot's freshest action with the same seqlock. The benchmark's `producer_shm` /
  `make_shm_consumer` are a working reference for both ends.

If a native shared-memory trap proves awkward to land inside the QVM/trap boundary, the
**unix-domain datagram socket** is the drop-in fallback (also measured, also under
budget); the file path stays available as a debug tap.

## Environment limit — read this before trusting the number on-server

This is a **host-local microbenchmark**. It measures transport cost on **this machine
only**. It does **NOT** run the real KTX server — there is no server build or SSH in this
sandbox. The numbers above prove the *transport itself* is far inside budget; they do
**not** prove the end-to-end on-server cost (QVM/trap call overhead, the server's actual
frame scheduler, real OS load on the game box).

**The on-KTX end-to-end p99 must be validated when the pipe is actually wired into the
moveprobe patch — that is ticket T0.3.** No on-server numbers are claimed or fabricated
here. What is proven: the chosen transport mechanism (`shm`, seqlock, 32-byte action,
4 slots @ 77 Hz) clears p99 < 0.5 ms/tick with ~40× margin in a faithful host-local
producer/consumer model.
